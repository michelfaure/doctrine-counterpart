## Décisions tranchées

1. **Architecture deux-hooks single responsibility** : `r15-autonomous-counter.sh` ne fait QUE compter et reset, `r15-commit-gate.sh` ne fait QUE bloquer. Contrat partagé minimal = state file JSON. Refusé l'option d'un script monolithique pour faciliter l'évolution future (V3, V4…) sans toucher au counter.

2. **Pas de V3 sur `git commit --amend`**. Le regex existant `git[[:space:]]+commit([[:space:]]|$)` matche déjà toutes les variantes amend (6/6 testées matériellement, dont 3 BLOCK + 1 bypass ack). Le claim "limite résiduelle V3-candidate" écrit hier soir était une révision sans nouveau fait — réfuté par sonde avant toute écriture de code. Mémoire corrigée.

3. **Pas d'extension à `git rebase --continue` / `git cherry-pick` / `git revert`**. Hors scope R15 — le compteur cible l'autonomie d'invocations Agent, pas toute opération git créatrice de commit. Décision actée par Michel Faure ("ok hors scope").

4. **Convention bypass identique à `deploy-safeguard`** : `[autonomy-ack]` n'importe où dans la commande, canonical en trailing comment. Réutilise la même grammaire pour ne pas multiplier les conventions.

## Apprentissages méthodo

1. **R5 (no revision without new fact) s'applique aussi aux claims posés en fin de session précédente**. Hier soir, en clôture, j'ai noté une "limite résiduelle V3-candidate pour `git commit --amend`" sans la tester. La sonde matérielle de ce matin (6 variantes testées) renverse le claim — V2 couvre déjà tout. Pattern : tout "TODO V-suivante" ou "limite résiduelle" non testé est un claim faible qui doit être tagué `[unverified]` ou matérialisé sur le moment. La discipline R5 ne se relâche pas au close.

2. **La phase de clôture est statistiquement le moment de production de claims faibles**. La fatigue post-session + le besoin de "boucler proprement" pousse à projeter des extensions futures non testées. C'est ironique parce que /close-session est précisément le protocole qui prêche la rigueur (R13). Conséquence opérationnelle : la section "À suivre" d'un session log doit être traitée comme une zone à risque, pas comme un fourre-tout libre. Soit la limitation est mesurée, soit elle est marquée comme hypothèse à tester.

3. **Single responsibility hooks confirmée empiriquement par évolutivité**. Les deux scripts séparés (counter / gate) ont permis d'ajouter la V2 sans toucher au counter — zéro régression possible sur la V1. Si j'avais fusionné les deux en un seul script "r15-meta-hook.sh" hier, l'extension V2 aurait demandé un refactor multi-fonction, augmenté la surface de test, et risqué de casser le counter en touchant le gate. Le coût initial "deux scripts" a été récupéré dès la première extension. Pattern : pour les hooks à logique évolutive, préférer N petits scripts avec contrat partagé minimal (state file JSON) à 1 script monolithique avec argv branching.
