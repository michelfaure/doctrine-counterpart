## Candidat 1 (FORT) — R17 : *Materialized state over stored proxy*

**Énoncé proposé** :
> *"A stored value (an external ID present, a `used_at` timestamp set, `max(created_at)`, a free-text note, a UI badge) is a CLAIM about intent or identity — not a materialized system state. Before asserting that a process succeeded, or before generating any external communication that depends on it, re-derive the real state from the authoritative source (round-trip API call, SQL read of the actual rows the application reads, recomputation of the derived value). The presence of a proxy is necessary, never sufficient. This extends R1 ('UI rendering is authority over the data model') one layer deeper: even inside the DB, a stored column can be a stale proxy for a truth that lives elsewhere."*

**Fondement matériel (N≥5, substrate rembrandt, base neuve vérifiée)** :
- `feedback_token_used_at_pas_dossier_finalise.md` (25/05) — `used_at` ≠ inscription 26-27 finalisée (35 % de faux positifs). 🔎 incident SetupIntent « réussi » lu depuis `stripe_setup_intent_id` non-null sans round-trip Stripe (attribution CLIENT-A 27/05 à vérifier).
- `feedback_id_externe_db_ne_vaut_pas_etat_systeme.md` (27/05) — ID externe en DB ≠ état système ; round-trip API obligatoire.
- `feedback_note_libre_db_intention_pas_etat.md` (11/06) — note libre DB = intention, pas état ; simuler ce que le code lit.
- `feedback_derniere_ligne_created_at_proxy_fragile.md` (11/06) — `max(created_at)` ≠ ligne du dossier (doublons annulés postérieurs) ; résoudre par FK ou `NOT EXISTS`.
- `feedback_ui_badge_soustraction_deux_caches.md` (11/06) — badge = diff de 2 caches ; le drift s'affiche en objet fantôme ; sonder la table source.
- `feedback_resolution_contact_par_email_doublon.md` (11/06) — résoudre un contact par email = doublon ; prioriser FK `contact_id`, email en fallback.
- (corpus ancien convergent : `memoire_verification_canonique`, `external_ai_visual_rendering_not_material`, `audit_db_pre_flight_canonique`, `lire_ui_avant_prescrire_donnee`.)

**Anti-pattern nommé** : *"asserter ou communiquer un état système depuis un proxy stocké (ID présent, used_at posé, max(created_at), note libre, badge) au lieu de re-dériver depuis la source autoritaire."*

**Tension avec règles existantes (à trancher par `/challenger`)** :
- **R1** dit déjà *"DB schema is authority over TS"* et *"UI rendering is authority over the data model"*. R17 ajoute une 3e couche : *au sein même de la DB*, une valeur stockée peut être un proxy périmé. Distinct ? **À falsifier** — risque de redondance comme Am.R1 retiré en v0.7. Argument pour distinct : R1 traite des couches (TS < DB < UI) ; R17 traite de la nature (proxy stocké vs vérité dérivée), orthogonal aux couches.
- **R6** (Live/Snapshot/Cache) : R17 est le versant *lecture* de R6. R6 dit comment *stocker* une valeur dérivable ; R17 dit qu'avant d'*agir* sur une valeur stockée, on re-dérive. Complémentaires.
- Verdict probable : **Am.R1 plutôt que R17 autonome**, sauf si `/challenger` établit l'angle distinct. Décision Michel Faure requise.

**Maturité** : 🟢 HAUTE. N≥5 base neuve + corpus ancien. Mécanisme direct. Candidat le plus solide de v0.8.

## Candidat 2 (FORT) — Am.R9/R16 : *Sub-agent worktree isolation does not survive compaction*

**Énoncé proposé (ajout à R9 §Sub-agent briefing ou R16)** :
> *"A sub-agent's worktree isolation is not durable across a context compaction. The compaction drops the worktree instruction; subsequent sub-agent `Edit` operations land on the main branch's working tree, and inter-chantier `stash pop` collides on a now-shared stack. For any sub-agent session expected to cross a compaction (>2h or >3 PR): the isolation must be enforced by a git mechanism (a real `git worktree add` on a separate path, verified by the parent post-compaction), not by a prompt instruction the compaction can erase. Note the asymmetry: a sub-agent's `Write` operations persist to the shared tree, but `Edit` operations can evaporate from the main working tree on socket death — never rely on a sub-agent's uncommitted Edit surviving."*

**Fondement matériel (N≥2 structurel, rembrandt)** :
- `feedback_subagent_worktree_isolation_perdue_compaction.md` (12/06) — sub-agent worktree : commits sur main post-compaction + stash pop inter-chantiers (pile partagée).
- `feedback_subagent_no_commit_push_deploy.md` (29/05) — 🔎 agent rembrandt a committé sur main + appliqué 2 migrations prod malgré brief explicite l'interdisant (attribution ADR-0089 à vérifier). Hook `[migration-ok]` institué en réponse.
- `feedback_workspace_partage_worktree_obligatoire.md` (25/05) — sessions >2h ou >3 PR = worktree par défaut (le déclencheur, pas encore le mode d'échec compaction).
- `feedback_agent_erp_build_verification.md` (09/06) — 🔎 récidive sur 5 sessions distinctes ; conclusion d'escalade « ne plus déléguer l'écriture des RPC critiques » (à vérifier).

**Anti-pattern nommé** : *"se fier à l'isolation worktree d'un sous-agent pour survivre à une compaction — l'instruction s'évapore, les Edit atterrissent sur main, les stash pop entrent en collision."*

**Tension** : v0.7 Am.R9 a traité la transmission des feedbacks load-bearing (« sub-agents do not transitively inherit memory »). Ce candidat traite un mode d'échec orthogonal : même un brief parfait s'évapore à la compaction. R16 mécanisme 1 (« scope matériel strictement non-chevauchant ») suppose le scope durable — la compaction le casse. **Angle mort réel non couvert.**

**Maturité** : 🟢 HAUTE. Mode d'échec nouveau, mécanisme clair (compaction = perte d'instruction ; Edit vs Write asymétrie). N=2 structurel suffisant vu la gravité (commits prod non voulus).

## Candidat 3 (MOYEN, probablement project-scope) — *DB-constraint phase-0 enumeration*

**Énoncé proposé (extension R8 phase-0 OU rule projet rembrandt)** :
> *"Phase 0 of any feature touching the DB enumerates the actual constraints, not just the symbols: `\d+ <table>`, `pg_constraint`, partial-index predicates, FK actions, CHECK clauses, Supabase default GRANTs. `tsc --noEmit` green is silent on all of them. Named silent-failure classes: FK `ON DELETE SET NULL` + column `CHECK NOT NULL` → the DELETE fails silently; FK SET NULL on a live business state → orphans a signed-contract phantom; a partial-index predicate (`WHERE statut = 'annule'`) drifts the moment a flow writes a synonym (`annulee_dossier_expire`); a PostgREST upsert cannot target a partial index."*

**Fondement matériel (N≥6, rembrandt — mais MONO-SUBSTRATE)** :
- `feedback_db_constraints_phase_zero.md` (05/06) — avant feature : lister UNIQUE/CHECK/FK DB.
- `feedback_fk_setnull_check_notnull_silent_delete.md` (12/06) — FK SET NULL + CHECK NOT NULL = DELETE échoue.
- `feedback_fk_setnull_orphan_etat_metier_actif.md` (12/06) — FK SET NULL « safe » orphelinise un contrat signé fantôme ; fix = flow, pas index.
- `feedback_index_partiel_predicat_statut_canonique.md` (05/06) — prédicat index partiel = tout le vocabulaire statut.
- `feedback_contrainte_unique_scope_perimetre_metier.md` (05/06) — index unique scopé au périmètre actif.
- `feedback_postgrest_upsert_index_partiel.md` (11/06) — upsert PostgREST ne cible pas un index partiel.

**Anti-pattern nommé** : *"traiter `tsc` vert comme DB-safe ; déléguer un DELETE/UPDATE sans avoir lu pg_constraint."*

**Tension** : extension naturelle de R8 (phase-0 grep des *symboles*) vers phase-0 des *contraintes*. ET de R1 (« DB schema is authority over TS »).

**Maturité** : 🟡 MOYENNE pour le toolkit. N≥6 mais **stack-spécifique** (Postgres/Supabase ; gorgon/Godot n'a pas de contraintes SQL). ## Candidat 4 (MÉTA, le plus stratégique) — R18 : *The doctrine is a data table subject to R6 and R13*

**Origine** : rapport insights agent 2026-06-13 §5 (angle non-évident), corroboré par le clustering de ce fichier.

**Constat matériel** : Michel Faure applique aux données Postgres une doctrine anti-drift impeccable (Live > duplication, audit trimestriel, source unique, test anti-tautologie) qu'il **n'applique pas à sa propre doctrine**. Asymétrie capture/retrait :
- Mécanisme de *création* riche : incident → feedback + ADR + entrée PILOTAGE-IA + parfois hook. 127 feedbacks, 16 règles, 12 skills, N hooks.
- Mécanisme de *retrait* : un seul audit mensuel, que le CLAUDE.md lui-même qualifie d'insuffisant (« le `mtime > 30 j` n'est PAS un critère suffisant »).
- Plusieurs feedbacks portent une probe-fantôme explicite « retirer si revient vide après 30 j » (`ancien_avec_inscription_active_anomaly`, `contact_introuvable_mailchimp_drift`) — 🔎 **aucune trace dans le corpus qu'une seule ait été exécutée puis retirée** (à vérifier matériellement avant de figer ce constat).
- Règles promues à N=1/N=2 (R9 « N=1 structural », R15 « N=1+1 ») jamais falsifiées par répétition. Combien des 127 feedbacks ont été *invalidés* par un incident contraire ? 🔎 le rapport en trouve zéro — statistiquement suspect après 80 jours.
- Métrique M1 (récurrence anti-pattern / 7j) : cible ≤1, **mesurée 12,33**, heuristique flaggée « over-sensitive » — et pourtant le rythme d'ajout ne ralentit pas. (M1 vérifié dans CLAUDE.md R13.)

**Énoncé proposé** :
> *"The doctrine corpus (rules, feedbacks, skills, hooks) is itself a data table and obeys R6 and R13. Concretely: (a) every feedback carrying a 'retire if empty after 30d' probe is a Snapshot with a HARD expiry, executed by a doctrine cron — not a manual audit; (b) any rule amendment grounded in N<3 incidents is tagged `[provisional]` like an R14 spike, and is either confirmed by a 3rd material incident within a window or demoted; (c) a feedback-DEATH metric (retired/month) must exist alongside the feedback-BIRTH metric — a corpus that only grows is a whitelist that lengthens per incident until it lies, the exact drift mode the doctrine teaches to hunt in `semantic_layer_drift_db_silent`, `filtre_whitelist_source_fragile`, `index_partiel_predicat_statut`."*

**Anti-pattern nommé** : *"faire croître la doctrine de façon monotone — capture sans retrait — en sur-déclenchant (M1=12,33) sans jamais retirer ni falsifier ; appliquer aux données une discipline anti-drift qu'on s'exonère d'appliquer à soi-même."*

**Tension** : R13 dit déjà *"the doctrine itself is versioned and audited like an ADR"* et prévoit l'audit trimestriel. R18 est plus tranchant : R13 audite l'*exactitude* (« est-ce encore vrai ? ») ; R18 impose un *mécanisme de mortalité* (expiry dur + métrique de décès + tag provisional auto-rétrogradant). R13 = relecture ; R18 = cron + métrique + falsification forcée.

**Maturité** : 🟢 HAUTE comme candidat (mécanisme clair, s'auto-applique, corrige un angle mort documenté). Mais 🔎 **dépend d'une vérification** : exécuter réellement les probes-fantômes et compter les retraits historiques avant de figer « zéro retrait ». Si le compte réel de retraits > 0, l'énoncé s'assouplit.

**Auto-application immédiate** : ce fichier `v0.8-candidates.md` doit lui-même naître avec une date d'expiration de candidats. Tout candidat ci-dessus non promu ni explicitement reconduit au prochain checkpoint est *retiré*, pas laissé en suspens.
